# L1 Two-Entry MSHR — v1.3 Design and Implementation Contract

**Status (2026-11-19):** the design described here has progressed beyond the
original queued-entry proposal. The current working-tree snapshot implements
two per-L1 miss contexts, same-core Directory issue, transaction-ID grant/refill
routing, shared Snoop control, L1 refill/metadata arbitration, and ordered
same-core miss responses. The focused acceptance suite and full-system pytest
results are recorded in
[`docs/dv/v1.3_nonblocking_l1_validation.md`](dv/v1.3_nonblocking_l1_validation.md).

This file preserves the earlier two-entry tracker proposal for design history;
its single-issued-miss/queued-second-miss descriptions below are superseded by
the implementation status and Phase 2 contract. `coherence_verify` did not
finish its Benchmark v4 stage in the latest run, so this is not a release or
PPA sign-off.

The sections below the original proposal are historical design notes. For the
current interface contract, measured two-context behavior, test commands, and
remaining gaps, use the 2026-11-19 implementation refresh in the linked DV
report and [`l1_miss_under_miss_v1_3_phase2_contract.md`](l1_miss_under_miss_v1_3_phase2_contract.md).

## Goal and scope

Each of the two L1s may retain two different-line CPU misses concurrently, so
the subsystem can accept and track four independent CPU miss requests before
the first response completes. Each L1 still has one MESI controller. Its first
miss owns that controller; the second miss occupies a queued MSHR and is
dispatched after the first request retires. Consequently the design supports
two accepted outstanding misses per core, but at most one controller-issued
miss per core at a time. The existing four Directory contexts, four refill
MSHRs, shared L2 data port and AXI adapter are unchanged. A four-entry L1
occupancy does not imply four active Directory contexts, refills or AXI reads.

This is the smallest interface-compatible step toward a non-blocking L1. It
does not implement two simultaneous same-core Directory transactions.

## CPU request and response contract

- The CPU request interface has `valid/ready`, address, operation, byte mask
  and write data, but no request ID input. We therefore do not add a Request
  ID in this change.
- CPU responses retain the existing address, operation, data and internally
  allocated transaction ID outputs. The transaction ID is generated by the
  controller when a queued request is dispatched; it is not an upstream tag.
- Misses from one core are dispatched and completed in acceptance order. A
  second miss cannot pass an earlier miss from that core.
- The existing Hit-under-Miss behavior remains: an eligible resident read hit
  can complete while that core's miss is pending, and may therefore be
  observed before the older miss response. The interface does not promise
  global in-order completion across hits and misses. The two cores are
  independent and may complete in either order.
- An upstream LSU that needs arbitrary response reordering must provide a
  request tag in a future interface revision. No such capability is inferred
  from the cache-generated transaction ID.

## MSHR allocation and lifecycle

Each core has two entries. An entry records the byte address, read/write,
write data, byte mask, valid state, active/queued role, and the downstream
transaction ID once its Directory request is accepted.

1. The first accepted request that needs coherence service allocates an active
   entry and follows the existing replacement/replay/controller path.
2. A second different-line request needing coherence service may allocate the
   other entry while the first controller is sending or awaiting its grant,
   provided the replacement engine and snoop/array resources are idle.
   This enqueue does not issue a second Directory request.
3. The active entry retires only when its CPU response handshakes. The
   controller also waits for the existing grant-commit handshake before
   returning idle.
4. The queued entry then becomes active and performs a fresh array lookup and
   replacement check before controller dispatch.
5. Reset clears both entries. A controller protocol-fatal error remains
   fail-stop as in the existing design; reset is required to recover it.

The ready signal deasserts for a third independent miss while both entries are
valid. The requester must hold valid and payload until accepted. The current
resident-read Hit-under-Miss bypass is enabled only while exactly one miss
context is live. When both MSHRs are occupied, even a resident read hit is
backpressured. Extending the bypass to two live misses needs separate proof of
lookup/refill array-port arbitration, response-slot behavior, and transaction-ID
uniqueness; it is not claimed by this implementation.

## Conflict and resource rules

- **Same line:** do not merge requests in v1.3. A request matching either
  valid MSHR line is backpressured. After the earlier request retires, the
  held request is looked up again and proceeds as a hit, upgrade or miss.
- **Store:** a different-line store can occupy the queued entry with its full
  data and byte mask. A same-line store is serialized and looked up again
  after the earlier request. No store is applied before refill/ownership is
  ready.
- **L1 array:** only the active controller owns the replacement/refill path.
  Queue allocation captures payload only and does not access array write
  ports. Queued dispatch waits for controller idle, no replacement operation,
  and no active/accepted snoop, then performs a fresh lookup. This preserves
  the existing single-port arbitration rules.
- **Replacement:** a second miss is not accepted while replacement owns the
  array or is waiting for Put/PutAck/transfer. The queued miss independently
  chooses its victim after dispatch. Existing PutS/PutE/PutM and owner-data
  snoop progress rules are retained.
- **Snoop:** queued requests are not yet Directory sharers and hold no L1
  array way. A queued request re-looks up state when dispatched, after any
  intervening snoop. The active transaction follows existing MESI snoop and
  stale-upgrade handling. Same-victim replacement/snoop serialization is
  unchanged.
- **Reset:** accepted entries are canceled with the existing whole-subsystem
  reset contract. No response is promised for canceled requests. Late-response
  behavior after reset is constrained by the existing downstream reset and
  transaction-ID contract and remains a verification point.
- **Shared L2/Directory/AXI:** no capacity or arbitration parameters change.
  Different cores may use separate downstream contexts concurrently. Within
  one core, only the active entry can consume a Directory context/refill/AXI
  request. All resource peaks must be reported separately.
- **Backpressure:** entry allocation is a CPU request handshake. A queued
  entry holds its payload stable until dispatch. Directory, refill, AXI,
  response and snoop backpressure continue to use their existing handshakes.

## Verification contract

The required concurrency test sends two distinct cold misses to each core,
with distinct cache lines/sets and delayed memory. Before releasing any CPU
response, it must observe four valid L1 MSHR entries. It separately samples:

- L1 MSHR valid/active occupancy (maximum accepted/active requests);
- Directory context occupancy;
- refill MSHR occupancy;
- AXI read/write outstanding counts.

The test checks all returned addresses/data and same-core miss order. A
different-core AXI response may return out of order and must route by AXI ID.
Additional directed tests cover full backpressure, same-line serialization,
response association, snoop/replacement collision, reset cancellation, and
PutM/owner-data progress. The existing blocking baseline benchmark remains
immutable; v1.3 results are written as a separate run and must describe the
actual resource level measured.

## Explicit non-goals

- Two simultaneous same-core misses issued into Directory.
- Four simultaneous Directory contexts/refill streams/AXI reads.
- Same-line MSHR merge or arbitrary same-core response reordering.
- L2 banking, extra array ports, Directory context-count changes, or PPA.

## RTL preparation checkpoint

`MesiL1Controller`'s existing single-miss transaction FSM has been extracted
into `rtl/l1/MesiL1MissContext.sv`. The controller still instantiates exactly
one context and retains its existing external ports and request/response
behavior. The optional external transaction-ID input on the context is
disabled by the compatibility wrapper. This is a structural preparation for
future context replication; it does not add Miss-under-Miss, a second
controller-issued request, or additional L1 array bandwidth. The context must
not be replicated until response routing, refill/metadata arbitration,
replacement and snoop conflicts have a matching RTL design and directed
system-level evidence.

The next P2 step is to evaluate true per-core Miss-under-Miss only after the
two-entry tracker passes the directed lifecycle suite and benchmark evidence
shows the per-core issue serialization is the limiting factor.
