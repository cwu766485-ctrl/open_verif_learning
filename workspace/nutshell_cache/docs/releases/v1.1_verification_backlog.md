# v1.1 Verification Backlog: Legal Recovery Paths

This backlog tracks legal or recoverable protocol paths that were not hit by
the 2026-10-28 integrated subsystem LCOV run. It is a follow-up plan, not a
claim that each path is functionally broken. Some may already have module-level
evidence; the goal is to add integrated stimulus, independent checking, and
explicit closure evidence where needed.

## Planned closure

| ID | Path | Required stimulus | Checker / pass condition |
| --- | --- | --- | --- |
| RCV-01 | Directory sees GetM from the core already recorded as owner | Create a valid owned line, issue GetM from that owner, then issue a remote conflicting request | Follow the MESI contract for retry/grant; check data, single-writer permission, owner/sharer metadata, and that both transactions retire |
| RCV-02 | Stale Upgrade recovery | Invalidate or otherwise remove the requester's shared copy before its Upgrade is serviced; keep a competing request active | Check the spec-defined recovery path, no stale sharer bit, correct final data/permission, and no duplicate or lost response |
| RCV-03 | Snoop ACK/INV_ACK without owner data followed by L2 retry | Force the Directory to request owner data while the target L1 no longer has the line; retain the authoritative L2 copy | Verify the ACK type, L2-sourced refill data, final Grant and Directory state, and exactly-once completion |
| RCV-04 | MSHR arbitration lock under backpressure | Stall Directory write, Snoop, transfer-start, and Grant offers in turn while changing competing context requests | Assert offered payload/address/ID stability; after ready returns, verify correct context selection, no duplicate side effect, and eventual completion under bounded fairness assumptions |
| RCV-05 | L1 E/M Snoop read misses after concurrent metadata removal | Accept a Snoop for an E/M line, remove the line through a competing legal replacement/invalidation sequence before array data returns | Verify no-data response, preserve Directory authority, perform the allowed L2 retry, and compare all returned data beats |
| RCV-06 | Replacement replay after same-set Put/Snoop conflict | Run the same-set replacement/Snoop admission conflict with each core as Put source and each core as Snoop target | Check victim address/opcode, no stale L1 copy, final Directory owner/sharer state, and bounded transaction retirement |

## Closure rules

1. Start from a legal MESI state produced through accepted CPU/protocol
   transactions; do not seed internal DUT state to manufacture the scenario.
2. Use a Python/Toffee sequence plus independent data and Directory checkers.
   Retain a failing seed and a concise replay if random traffic discovers a new
   ordering.
3. Record Feature → Testpoint → Stimulus → Checker → Coverage mapping. Coverage
   is only credited after the checker passes for the observed transaction.
4. Add bounded formal properties only where their fairness and environmental
   assumptions can be stated precisely. A bounded pass is not an unbounded
   liveness proof.
5. Keep malformed input/error-injection tests separate from legal recovery
   tests. Do not waive a legal recovery path just because its line is currently
   unhit.

The source-level candidate list and line ranges are maintained in the
[Coverage Gap Review](../coherence_coverage_gap_review.md). PPA, SRAM mapping,
and STA are outside this verification backlog.
