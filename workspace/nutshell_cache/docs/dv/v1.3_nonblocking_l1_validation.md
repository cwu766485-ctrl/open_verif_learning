# NutShell Cache v1.3 — Two-entry L1 MSHR validation

**RTL source commit:** `fb9db8b8ef20fa0091293b41726b5667eda3c015` · **Branch:** `codex/v1.3-nonblocking-l1`
**Decision:** targeted implementation evidence passes; full regression/sign-off remains open.

This change adds two miss-tracking entries to each L1 while retaining the existing
MESI controllers and downstream interfaces. It is an incremental v1.3 step, not a
four-way downstream miss engine.

## Interface and ordering contract

The LSU request interface has no incoming request ID, so this change does not add
one or alter the CPU interface. Each L1 dispatches and completes its misses in
acceptance order. Its generated transaction ID is allocated on dispatch and is
not an upstream request tag. The two cores are independent and may complete in
either order. The existing resident-read Hit-under-Miss path remains allowed to
respond before a pending miss. A future design that allows arbitrary same-core
miss completion order will need an explicit request tag or a compatible LSU
ordering contract.

Each L1 can accept two distinct-line, coherence-serviced requests that have not
yet received CPU responses. The first uses the existing controller. The second
is retained in the queued MSHR and re-looked-up when dispatched. A third such
request is backpressured. Same-line requests are serialized rather than merged;
queued stores retain data and byte mask and only execute after the usual lookup,
permission, and refill path. Reset clears both entries under the existing reset
contract. MESI, Shared L2, Directory, AXI, MMIO, and APB ports and capacities are
unchanged.

The queue does not issue two same-core coherence transactions at once. Thus the
four-entry L1 occupancy is distinct from downstream concurrency: the existing
per-core controller permits at most two issued misses total, so Directory
contexts, refill MSHRs, and AXI reads each peaked at two in the four-entry test.
No L2 banking or Directory capacity change was made.

## Four independent CPU misses: measured evidence

The test `test_four_l1_misses_occupy_two_entries_per_core` ran on the AXI
subsystem with seed `1246212` (`0x130404`). It issued two cold lines per core:

| Core | First line | Second line |
| --- | ---: | ---: |
| CPU0 | `0x00410008` | `0x00410088` |
| CPU1 | `0x00410108` | `0x00410188` |

All four lines map to distinct cache lines and sets. The memory delay was 140
cycles; AXI R used a 2-cycle valid-gap pattern and a reorder window of 3. The
agent reversed the first two AXI read IDs. Before the first CPU response, the
monitor observed all four L1 MSHR entries valid; occupancy was four for 381
sampled cycles. The per-core maximum was two.

The resource measurements are deliberately separate:

| Resource | Measured peak | Meaning |
| --- | ---: | --- |
| Accepted/outstanding L1 MSHR entries | 4 | Two per L1, before CPU responses |
| Issued L1 controllers | 2 | One active controller transaction per core |
| Directory contexts | 2 | Queued L1 MSHRs do not allocate contexts |
| Refill MSHRs | 2 | Two line refills active at once |
| AXI read outstanding | 2 | AXI IDs routed across the two active refills |
| AXI write outstanding | 0 | This read-only scenario has no writeback |

The independent `L1MshrLifecycleChecker` checked six accepted requests in the
whole test, their address/data association, per-core miss order, and response
cycles. For the first four lines it observed responses in this order:

| Core / address | CPU response cycle | Directory transaction ID | AXI ID |
| --- | ---: | ---: | ---: |
| CPU1 `0x00410108` | 196 | 0 | 1 |
| CPU0 `0x00410008` | 205 | 0 | 0 |
| CPU1 `0x00410188` | 398 | 1 | 0 |
| CPU0 `0x00410088` | 407 | 1 | 1 |

This demonstrates cross-core completion reordering and correct AXI ID association.
It does not demonstrate same-core out-of-order miss completion. The refill
lifecycle checker also observed 6 MSHR allocations/retirements and matched all
48 AXI beats to all 48 L2 refill beats. CPU requests accepted/completed were 6/6;
protocol, fatal, and AXI error counts were zero.

The sampled Functional/Cross Coverage bin maps for this standalone test are
empty. The evidence is monitor events plus the independent lifecycle check; this
test must not be counted as closing unrelated Functional Coverage bins.

## Local validation refresh — 2026-11-18

separate Cross-Closure failure was found in CR05's monitor semantics: the
same-set Directory request can be stalled by the active refill lookup before
the Directory emits a Snoop. The former event was sampled only at the later
Snoop-set-conflict point, so it missed this real admission stall. The monitor
now distinguishes `directory.same_set_conflict` at refill lookup from
`directory.snoop_set_conflict`; the CR05 checker also verifies both line
addresses and their common L2 set.

## Remaining work and release status

This is not a complete v1.3 or v1.1 release sign-off. The following were not run
in this round: `coherence_verify`, full-system full/stress regression, Formal,
RTL code-coverage audit/release gate, Mutation, GitHub Actions, and PPA/STA.
Targeted scenarios passed, but they do not establish all reset epochs, late AXI
responses after reset, every same-set/snoop/replacement interleaving, or broad
random closure.

True same-core Miss-under-Miss is now the requested v1.3 next phase. Its
interface, ordering, transaction association, array arbitration, conflict
policy and acceptance tests are frozen as an OPEN design contract in
[`../l1_miss_under_miss_v1_3_phase2_contract.md`](../l1_miss_under_miss_v1_3_phase2_contract.md).
The next RTL increment must separate multiple active coherence transactions
from the current single MESI controller and arbitrate the shared L1 array across
lookup/refill/store/snoop/replacement. Benchmark changes follow only after
directed checkers prove that same-L1 misses are actually issued concurrently.
