The current snapshot adds two independent miss contexts to each L1 while

## Interface and ordering contract

The LSU request interface has no incoming request ID, so this change does not add
one or alter the CPU interface. Each L1 dispatches and completes its misses in
acceptance order. Its generated transaction ID is allocated on dispatch and is
not an upstream request tag. The two cores are independent and may complete in
either order. The existing resident-read Hit-under-Miss bypass remains enabled
with exactly one live miss context and may respond before that miss. With both
MSHR entries occupied, the bypass is currently backpressured; safe progress in
that condition is not claimed. A future design that allows arbitrary same-core
miss completion order will need an explicit request tag or a compatible LSU
ordering contract.

Each L1 can accept two distinct-line requests before the earlier miss response
retires. Each context has its own downstream transaction association; Grant and
Refill are matched to the corresponding live transaction ID. The existing
single Snoop engine is shared, and refill line ownership plus metadata/store
writes are arbitrated against the L1 array. A third request is backpressured.
Same-line requests are serialized and re-looked-up rather than merged. The
public CPU interface has no request ID, so miss responses retire in same-core
acceptance order; the existing resident-read Hit-under-Miss bypass remains a
separate response class. MESI, Shared L2, Directory, AXI, MMIO and APB public
interfaces are unchanged.

The measured four-miss case reaches two issued L1 contexts per core and four at
each of the Directory, refill-MSHR and AXI R layers. AXI W outstanding is zero
because the scenario is read-only. No L2 banking or Directory capacity change
was made.

## Four independent CPU misses: measured evidence

The test `test_four_l1_misses_occupy_two_entries_per_core` ran on the AXI
subsystem with seed `1246212` (`0x130404`). It issued two cold lines per core:

| Core | First line | Second line |
| --- | ---: | ---: |
| CPU0 | `0x00410008` | `0x00410088` |
| CPU1 | `0x00410108` | `0x00410188` |

All four lines map to distinct cache lines and sets. The memory delay was 140
cycles; AXI R used a 2-cycle valid-gap pattern and a reorder window of 3. The
agent reversed the first two AXI read IDs. Before the first CPU response, the
monitor observed all four L1 MSHR entries valid; occupancy was four for 381
sampled cycles. The per-core maximum was two.

The resource measurements are deliberately separate:

| Resource | Measured peak | Meaning |
| --- | ---: | --- |
| Accepted/outstanding L1 MSHR entries | 4 | Two per L1, before CPU responses |
| Issued L1 controllers | 2 | One active controller transaction per core |
| Directory contexts | 2 | Queued L1 MSHRs do not allocate contexts |
| Refill MSHRs | 2 | Two line refills active at once |
| AXI read outstanding | 2 | AXI IDs routed across the two active refills |
| AXI write outstanding | 0 | This read-only scenario has no writeback |

The independent `L1MshrLifecycleChecker` checked six accepted requests in the
whole test, their address/data association, per-core miss order, and response
cycles. For the first four lines it observed responses in this order:

| Core / address | CPU response cycle | Directory transaction ID | AXI ID |
| --- | ---: | ---: | ---: |
| CPU1 `0x00410108` | 196 | 0 | 1 |
| CPU0 `0x00410008` | 205 | 0 | 0 |
| CPU1 `0x00410188` | 398 | 1 | 0 |
| CPU0 `0x00410088` | 407 | 1 | 1 |

This demonstrates cross-core completion reordering and correct AXI ID association.
It does not demonstrate same-core out-of-order miss completion. The refill
lifecycle checker also observed 6 MSHR allocations/retirements and matched all
48 AXI beats to all 48 L2 refill beats. CPU requests accepted/completed were 6/6;
protocol, fatal, and AXI error counts were zero.

The sampled Functional/Cross Coverage bin maps for this standalone test are
empty. The evidence is monitor events plus the independent lifecycle check; this
test must not be counted as closing unrelated Functional Coverage bins.

## Resource-monitor semantics audit — 2026-11-18

Review of the four-miss measurement found that the monitor exposed
`monitor_l1_mshr_valid` as both allocation and active occupancy, and treated
controller ownership as Directory issue. Those meanings were too broad for
resource claims. The monitor now reports three distinct L1 bitmaps:

| Observation | Definition |
|---|---|
| Allocated | Accepted request has a live valid L1 tracking entry |
| Controller-owned | Entry is selected by the per-core MESI controller |
| Directory-issued | Controller is in `WAIT_GRANT`, `REFILL`, `META_WRITE`, `RESP`, or post-issue `ERROR`, after leaving `SEND_REQ` |

Directory contexts, refill MSHRs, and AXI outstanding remain independent
measurements. On the four-cold-read workload, the observed peaks are four
allocated entries (two/core), one controller-owned and one Directory-issued
entry per core, two Directory contexts, two refill MSHRs, and two AXI reads.
This confirms two simultaneous controller transactions across the two cores,
not two issued misses within either core. The controller still serializes its
own second queued miss.

The 5-test MSHR regression passed after adding per-core occupancy histograms

Snoop path, and refill ownership plus metadata/store writes are arbitrated at
the shared L1 array. Miss responses retire in that core's acceptance order.
Same-line requests are serialized and re-looked-up rather than merged; a third
request is backpressured. The existing shared L2, four Directory contexts,
four refill MSHRs, AXI, MMIO, and APB capacities were not enlarged.

### Remaining implementation boundary

The exercised Snoop path can make progress while two misses are live. The
replacement PutM collision is still open: the second-miss admission predicate
currently rejects a request needing replacement (`!request_needs_replace`) and
requires the replacement FSM to be idle. The collision must be handled by a
transaction-associated replacement context before removing this serialization;
no claim is made that dirty replacement and two live misses are already
supported together. Miss-under-Miss coverage also does not establish every
possible Reset, Snoop, same-set, Store, and backpressure interleaving.
